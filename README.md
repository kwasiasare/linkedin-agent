# Spreadcom LinkedIn Agent

Automated LinkedIn presence manager for **Spreadcom LLC** — a Microsoft 365 Managed Services Provider based in Worcester, MA. The agent publishes daily content, monitors and replies to comments, tracks sales leads, and generates weekly analytics reports.

---

## What It Does

| Task | Frequency | How |
|---|---|---|
| Publish a LinkedIn post | Weekdays 8:00 AM EST | Claude generates content from rotating pillars |
| Monitor comments & reply | Weekdays 8:15 AM + 5:15 PM EST | Classifies each comment, generates a contextual reply |
| Log sales leads | On detection | Extracts intent, urgency, and follow-up suggestion |
| Weekly analytics report | Fridays 5:30 PM EST | Aggregates post stats + lead pipeline into a markdown report |

---

## Architecture

```
agent.js  (orchestrator — cron scheduling + CLI)
   │
   ├── content.js    ← Claude API (opus-4-5 for posts, haiku-3-5 for replies/classify)
   ├── linkedin.js   ← LinkedIn REST API client (base: api.linkedin.com/rest, v202602)
   ├── engage.js     ← Comment monitoring + reply loop
   ├── leads.js      ← Lead pipeline (data/leads.json)
   ├── report.js     ← Weekly analytics aggregation
   ├── logger.js     ← Winston logger (logs/agent.log + logs/errors.log)
   └── auth.js       ← OAuth 2.0 flow (run standalone: npm run auth)

data/
   ├── content_state.json   ← Pillar rotation state (survives restarts)
   ├── leads.json           ← Lead pipeline
   └── replied_comments.json ← Deduplication set for comment replies

logs/
   ├── agent.log            ← Rotating, max 5 MB × 7 files
   ├── errors.log           ← Error-only log, max 5 MB × 3 files
   └── report_YYYY-MM-DD.md ← Weekly reports (one per run)
```

## Environment Variables

All config lives in `.env` (never committed). Reference: `.env.example`.

| Variable | Description |
|---|---|
| `ANTHROPIC_API_KEY` | Anthropic API key for Claude |
| `LINKEDIN_CLIENT_ID` | LinkedIn Developer App — Client ID |
| `LINKEDIN_CLIENT_SECRET` | LinkedIn Developer App — Client Secret |
| `LINKEDIN_ACCESS_TOKEN` | OAuth 2.0 access token — generated by `npm run auth`, expires ~60 days |
| `LINKEDIN_ORGANIZATION_ID` | Numeric ID of the LinkedIn Company Page (from Page Admin > Settings) |
| `LINKEDIN_PERSON_URN` | `urn:li:person:XXXXXXXX` — the page admin's member URN; printed by `npm run auth` |
| `LINKEDIN_API_VERSION` | LinkedIn API version header, e.g. `202602` — update when `NONEXISTENT_VERSION` errors appear |
| `POST_TIME_CRON` | Cron expression for daily post (default: `0 8 * * 1-5`) |
| `ENGAGE_TIME_CRON` | Cron expression for engagement runs (default: `15 8,17 * * 1-5`) |
| `TIMEZONE` | Timezone for cron schedules (default: `America/New_York`) |

> **Access token expiry:** LinkedIn tokens expire after ~60 days. Re-run `npm run auth` to get a fresh token and copy the new value into `.env`.

## Authentication

`npm run auth` runs an OAuth 2.0 authorization code flow:

1. Opens the LinkedIn consent screen in your browser.
2. Starts a local HTTP server on `http://localhost:3000/callback` to receive the redirect.
3. Exchanges the authorization code for an access token.
4. Immediately tests the token against `/v2/me`.
5. Prints the token for you to copy into `.env`.

```bash
npm run auth
# Copy the printed LINKEDIN_ACCESS_TOKEN= line into .env
```

## Usage

### One-off tasks

```bash
npm run post      # Publish one post immediately (uses current pillar + sub-topic)
npm run engage    # Run one engagement cycle (check comments, reply, log leads)
npm run report    # Generate and save a weekly analytics report
```

### Daemon mode (scheduled)

```bash
npm start
# Runs all three tasks on their cron schedules and keeps the process alive.
# Press Ctrl+C to stop.
```

Scheduled times (all weekdays, America/New_York by default):

| Task | Default schedule |
|---|---|
| Daily post | 8:00 AM |
| Engagement cycle | 8:15 AM and 5:15 PM |
| Weekly report | Fridays 5:30 PM |

Override schedules via `POST_TIME_CRON` and `ENGAGE_TIME_CRON` in `.env`.

## Content System

### Pillars (rotate in order, state persisted to `data/content_state.json`)

1. `security_awareness` — Threat education for M365 SMEs
2. `product_education` — Deep dives on Intune, Entra ID, Defender, Autopilot, etc.
3. `cost_vs_value` — Financial framing: cost of inaction vs $20/user/month
4. `migration` — Exchange, SharePoint, AD → cloud migrations
5. `compliance_risk` — HIPAA, CMMC 2.0, NIST CSF, GDPR/CCPA
6. `sme_productivity` — Underused M365 features and their business impact
7. `engagement_poll` — Poll-format posts to drive comments
8. `thought_leadership` — Forward-looking insight, no hard CTA

Each pillar has 6–8 specific **sub-topics** (angles). The agent tracks the last 14 sub-topics used to prevent repetition. On exhaustion of a pillar's topics, it falls back to topics not used in the most recent 4.

### Character limits

Posts are capped at **1,300 characters** (LinkedIn's limit). A contact footer (`+1 774 570 0034 | spreadcomgh.com | info@spreadcomgh.com`) is always appended. The body is truncated at the last sentence boundary if needed.

### Models used

| Task | Model |
|---|---|
| Post generation | `claude-opus-4-5` |
| Comment classification | `claude-haiku-3-5-20241022` |
| Reply generation | `claude-haiku-3-5-20241022` |
| Lead extraction | `claude-haiku-3-5-20241022` |
| Weekly report summary | `claude-haiku-3-5-20241022` |

## Lead Pipeline

Comment classifications: `LEAD_SIGNAL`, `TECHNICAL_QUESTION`, `POSITIVE`, `NEGATIVE`, `SPAM`, `GENERAL`.

When a comment is classified as `LEAD_SIGNAL`, the agent:
1. Extracts `signal`, `service_interest`, `urgency` (high/medium/low), and `suggested_followup` via Claude.
2. Logs the lead to `data/leads.json` with status `new`.
3. Deduplicates: same commenter URN within 7 days is skipped.

Lead statuses (update manually or via `leads.js:updateLeadStatus`):
`new` → `contacted` → `qualified` → `booked` → `closed`

The weekly report includes a pipeline summary broken down by status and urgency.

## Phase 1 vs Phase 2

The agent ships in **Phase 1** (pre-Marketing Developer Platform approval):

| | Phase 1 | Phase 2 (post-MDP) |
|---|---|---|
| Posts authored as | `urn:li:person:...` (you) | `urn:li:organization:...` (company page) |
| Follower/page stats | Not available (403) | Available |
| Reactions API | Not available | Available |
| Feed comment scopes | Not needed | `w/r_organization_social_feed` |

**To activate Phase 2 after MDP approval:**

1. In `src/auth.js`, uncomment the Phase 2 `SCOPES` block.
2. Run `npm run auth` to get a new token.
3. In `src/linkedin.js`, change every `personUrn()` marked `// PHASE 1` to `orgUrn()`.

## LinkedIn API Notes

| Topic | Detail |
|---|---|
| Base URL | `https://api.linkedin.com/rest` (not `/v2`) |
| Version header | `LinkedIn-Version: YYYYMM` — required on every request |
| Active version | Update `LINKEDIN_API_VERSION` in `.env` if `NONEXISTENT_VERSION` errors appear. As of early 2026, `202602` is active. Safe range is approximately the last 12–18 months. |
| Post ID | Returned in the `x-restli-id` **response header** — the 201 body is empty |
| Comment URN | Use `comment.commentUrn` (composite URN) for replies, not `comment.id` (bare numeric ID) |
| Post text field | `post.commentary` (not `specificContent.shareCommentary.text`) |
| Post timestamp | `post.createdAt` (Unix ms, not `post.created.time`) |

## Logging

All structured logs go to `logs/agent.log` (info+) and `logs/errors.log` (error only). Both rotate at 5 MB. Console output mirrors the log stream.

```
[2026-04-08 08:00:01] INFO: Generating post — pillar: product_education, angle: Microsoft Intune...
[2026-04-08 08:00:04] INFO: Post created: urn:li:share:...
[2026-04-08 08:00:04] INFO: Daily post published (pillar: product_education, angle: ...) — ID: urn:li:share:...
```

Weekly report files are saved to `logs/report_YYYY-MM-DD.md`.
